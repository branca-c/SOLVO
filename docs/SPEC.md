# SOLVO MVP Specification

## 1. Product goal

SOLVO is an AI-assisted facility-maintenance work-order system. A requester describes a fault by text or browser-recorded audio. SOLVO turns it into an editable ODL (Ordine di Lavoro) draft, validates it, and creates the ODL only after user confirmation. Deterministic backend rules then route the work to the appropriate technical team and keep the operator dashboard current.

The MVP succeeds when its primary flow can be demonstrated clearly from intake through technician fulfillment and operator closure. AI assists interpretation; it does not own operational decisions.

## 2. Roles and surfaces

| Role | Responsibilities | Primary surface |
|---|---|---|
| Requester (`UTENTE`) | Submit text/audio, review and edit the draft, confirm the ODL, view its state, send reminders | Web portal |
| Operator (`OPERATORE`) | Monitor ODLs, assignments, urgent cases, reminders and closures; call the team lead when needed | Control Center |
| Technician (`TECNICO`) | Open the mobile request, accept or refuse it, add intervention details, mark it fulfilled | Mobile web page reached from the notification |

Authentication may be intentionally simple for the MVP, but authorization must still enforce role capabilities.

## 3. Controlled vocabulary

### Priorities

`PROGRAMMABILE`, `BASSA`, `MEDIA`, `ALTA`, `URGENTE`

### ODL statuses

`APERTO`, `IN_CORSO`, `EVASO`, `CHIUSO`, `ANNULLATO`

Labels may replace underscores for display only. Persist and exchange the exact values above.

### Initial categories

Vetri, Climatizzazione, Riscaldamento, Ascensore, Rete, Elettrico, Edile, Idraulico, Serramenti, Antincendio, Sicurezza, Arredi, Altro.

Categories must be stored in the database and remain extensible without application-code changes.

### Input origins

`TESTO`, `AUDIO`

## 4. ODL data

| Field | Required | Rule |
|---|---:|---|
| Code | Yes | Generated by the backend; unique and immutable |
| Created at | Yes | Server timestamp; immutable |
| Requester first and last name | Yes | Proposed from input or entered/edited by requester |
| Requester phone | Yes | Proposed from input or entered manually |
| Requester email | No | Optional |
| Fault address | Yes | Proposed from input or entered manually |
| Category | Yes | Active database category; AI may propose it |
| Priority | Yes | One of the five exact values; AI may propose it |
| Fault description | Yes | Normalized proposal reviewed by requester |
| Status | Yes | Initially `APERTO`; changed only by domain rules |
| People-risk flag | Yes | Boolean proposed by AI and reviewable by requester |
| Assigned technician | No | Empty at creation; set through routing/acceptance |
| Origin | Yes | `TESTO` or `AUDIO` |

Reminders are separate timestamped events. The existing `reminders_count` column is maintained atomically when a reminder is created and cannot be edited directly through the API.

## 5. Main flow

1. The requester submits a text message or records audio in the browser.
2. Audio is stored and transcribed through an audio/transcription provider. During local development, this provider is a fake or stub.
3. An AI provider returns structured proposed data: requester details, address, category, priority, description, and people-risk flag.
4. The backend validates required fields, allowed values, and category existence.
5. The requester sees an editable draft. No ODL exists until they explicitly confirm it.
6. On confirmation, the backend generates code/time, creates an `APERTO` ODL, and records its history event atomically.
7. The routing service selects the configured team for the category: Technician 1, Technician 2, Technician 3, then team lead.
8. A notification provider sends the current candidate a link to the technician mobile page. During local development, delivery is fake and inspectable.
9. The technician accepts or refuses. Refusal has only one optional `notes` field; it has no required reason.
10. Acceptance assigns the technician and moves the ODL to `IN_CORSO`. Refusal or no response advances routing to the next candidate.
11. Backend changes are broadcast to the Control Center through WebSocket without a page refresh.
12. The assigned technician records the work performed and moves the ODL to `EVASO`.
13. The operator reviews and moves it to `CHIUSO`.

## 6. Workflow rules

The backend is authoritative for transitions, routing, retry, escalation, reminders, persistence, and history.

| From | To | Actor/trigger | Conditions |
|---|---|---|---|
| creation | `APERTO` | Requester confirmation | Draft is valid |
| `APERTO` | `IN_CORSO` | Technician acceptance | Candidate is the current valid assignee |
| `IN_CORSO` | `EVASO` | Assigned technician | Work-performed details supplied |
| `EVASO` | `CHIUSO` | Operator | Operator confirms closure |
| `EVASO` | `IN_CORSO` | Explicit status request | Reopen fulfilled work |
| `APERTO` | `ANNULLATO` | Authorized user/operator | Cancellation is recorded |
| `IN_CORSO` | `ANNULLATO` | Operator | Cancellation is recorded |

Terminal statuses are `CHIUSO` and `ANNULLATO`. Invalid transitions return 409 Conflict. Same-status requests return 200 without changing the ODL or duplicating history, including in terminal states.

Routing order is configured per category. A refusal closes the current assignment attempt and starts the next one. A no-response retry follows the same deterministic sequence. If the sequence is exhausted, the ODL remains visibly unassigned/escalated for operator action; it is not silently accepted or closed.

For `URGENTE` plus people risk, the Control Center must strongly highlight the ODL and expose a direct call action for the team lead, bypassing the normal chain for human contact. SOLVO must clearly state that it does not replace emergency services (112/118 or law enforcement).

## 7. Surface requirements

### Requester portal

- Text input and browser audio recording.
- Processing feedback and recoverable errors.
- Fully editable structured draft before confirmation.
- ODL confirmation and status view.
- Reminder action that creates a timestamped reminder event.

### Operator Control Center

- Visual system defined in `docs/DESIGN_SYSTEM.md`.
- Summary cards and recent/all ODL table.
- Search and filters useful to the demo: code/text, status, priority, category, assigned technician.
- Live updates over WebSocket.
- Clear unassigned/routing state, reminders, urgent people-risk treatment, ODL detail/history, closure and cancellation actions.
- No SLA or "tempo aperto" metric.

### Technician mobile page

- Tokenized link identifies a currently valid assignment attempt.
- Essential ODL details and large touch targets.
- `ACCETTA` and `RIFIUTA` actions.
- Refusal contains only optional notes.
- For an accepted ODL, work-performed input and `EVASO` action.

## 8. AI and failure behavior

- AI output must conform to a versioned structured schema and pass backend validation.
- The user can correct every proposed business field before confirmation.
- The model never writes to PostgreSQL and never performs a status transition.
- Provider failure must preserve the original input and offer a clear retry/manual-completion path.
- Low-confidence or missing classification becomes a draft validation issue, not invented data.

## 9. Audit and acceptance criteria

Each material action records actor, timestamp, ODL, event type, and relevant non-secret metadata. At minimum: creation, assignment attempt, notification outcome, acceptance, refusal (optional notes), routing advance, reminder, status transition, work performed, closure, and cancellation.

The MVP is acceptable when a repeatable 2–3 minute demo can:

1. submit text or audio;
2. show and edit an AI-produced draft;
3. confirm and create an `APERTO` ODL;
4. route it and expose a mobile technician link;
5. accept or refuse (with optional notes only), reflecting the change live;
6. mark accepted work `EVASO`, then close it as operator;
7. demonstrate the urgent/people-risk treatment;
8. run without AWS by using local provider implementations.


## 10. Current WorkOrder API delivery

The scoped WorkOrder API uses existing persistence models and the contract in
`README.md`. The status endpoint enforces exactly these transitions:
APERTO → IN_CORSO/ANNULLATO, IN_CORSO → EVASO/ANNULLATO,
EVASO → CHIUSO/IN_CORSO; CHIUSO and ANNULLATO are terminal. Same-status
requests are no-op successes. Actor, assignment, and fulfillment-detail checks
from the full product flow are not part of this delivery.

The reminder POST requires `created_by` to reference an existing user because the
model does not allow null; no authentication is introduced. Reminder creation,
SQL counter increment, and history insertion are atomic. Each successful POST
creates a distinct reminder, regardless of ODL status. Reminder and history GETs
return only that ODL's records, newest first with descending ID as a tie-breaker.
Creation, actual status changes, and reminders append history; no-op updates do
not. Missing ODLs return 404, invalid transitions 409, and invalid input 422.

Category validation checks existence because the model has no active flag.
Physical ODL deletion removes related history through existing cascades. This
slice does not implement the complete product flow described above.
